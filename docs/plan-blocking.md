# План: «один проход за окно» через блокировку сотрудника

> **Статус (12.10.2026):** реализовано всё, кроме страховки через планировщик PERCo: она ждёт ночной проверки.
> Код: `internal/engine/blocker.go` (логика), `internal/store/blocks.go` (журнал), `internal/web/server.go` + `pin.go` (API),
> кнопка и панель в `internal/web/static`. Тесты: `internal/engine/blocker_test.go` (11 сценариев).
> Проверено на изолированном экземпляре: переключатель, PIN, блокировка перебора, `unblock-all`.

## Зачем
У столовой стоит только считыватель, без замка и турникета, поэтому штатный антипассбэк PERCo не работает
(при «Регистрации прохода по предъявлению» PERCo отключает Antipass). Повторный проход в одном окне можно запретить
только программно: после первого прохода служба временно блокирует сотрудника в PERCo, а после окна разблокирует.
Карта используется только в столовой, поэтому блокировка не мешает проходам в другие места.

## Как работает (пример)
- 07:31 Бақбай приложил карту, загорелся зелёный → событие 17 → служба видит его через 1–2 с.
- Окно «Завтрак» 07:05–08:15, у Бақбая это первый проход → служба записывает в свой журнал «блокирую до 08:15»,
  затем `POST /users/staff?ids=[900]` `{"is_block": true}`.
- 07:40 повторное прикладывание → **писк**, событие отказа → на экране «Отказ — уже был на завтраке».
- 08:15 окно закончилось, но блокировка **держится дальше**: карта не работает и вне окон.
- 11:59 → `{"is_block": false}` → за минуту до начала обеда (следующего окна этого сотрудника) карта снова работает.
- Если у сотрудника после этого окна нет другого окна сегодня (например, после ужина), блокировка держится до полуночи.
  Срок считается только по шаблонам самого сотрудника: без шаблона «Обед» после завтрака ждём ужина.

## Принципы надёжности
1. **При сомнении не блокируем (fail-open).** Блокировки нет, если окна питания не загружены, нет связи с PERCo,
   часы разошлись с PERCo больше чем на 2 минуты или режим не «ВКЛ». В этих случаях повтор только подсвечивается красным.
2. **Сначала журнал, потом действие.** Перед вызовом API служба записывает намерение в SQLite: кто, за какой приём пищи,
   до какого времени. Если служба упадёт между записью и вызовом, при старте она увидит запись и доведёт дело
   до конца или откатит.
3. **Снимаем только свои блокировки.** Если сотрудник уже заблокирован оператором, служба его не трогает и не запоминает.
   Если оператор заблокировал человека, пока у него стоит блокировка службы (в журнале PERCo это видно
   по другому `user_name`), служба его **не разблокирует**, а показывает предупреждение. Для этого службе нужен
   отдельный оператор `meal-service`.
4. **Несколько независимых способов снять блокировку:**
   | Механизм | Когда срабатывает |
   |---|---|
   | за минуту до начала следующего окна сотрудника (или полночь, если окон больше нет) | обычный случай; не раньше конца текущего окна |
   | старт службы | снимаются все блокировки с истёкшим сроком |
   | предельный срок | любая блокировка снимается не позже чем через `max_hours` (по умолчанию 16 ч), даже при ошибке в расчёте окна |
   | ночная проверка 00:05 | всё, что осталось со вчера |
   | переключатель «ВЫКЛ» | снимаются все блокировки службы немедленно |
   | команда `perco-meal.exe unblock-all` | вручную, даже если веб-интерфейс недоступен |
   | **страховка на стороне PERCo** | при блокировке служба создаёт в планировщике PERCo запись «Блокировка = нет» на завтра. Тогда сам сервер PERCo разблокирует человека в полночь, даже если наша служба не работает (*проверить на этапе 0*). |
5. **Повторы при ошибках сети:** если разблокировка не прошла, служба повторяет её с интервалом 15 с → 1 мин → 5 мин,
   а дашборд показывает красное «Не удалось снять блокировку: N человек».
6. **Служба Windows с автоперезапуском** (уже настроено) и запуском при старте компьютера.

## Действия администратора PERCo во время работы службы
Служба читает весь журнал PERCo, включая действия операторов: «Редактирование сотрудника» (501402) с описанием
«было/стало», «Блокировка сотрудника» (501404), разблокировку, записи планировщика и изменения временных зон.
По полю `user_name` она отличает свои действия (оператор `meal-service`) от действий людей.
Правило одно: **последнее слово за человеком.**

| Что сделал администратор | Как реагирует служба |
|---|---|
| Добавил или убрал шаблоны питания (например, выдал «Ужин») | Шаблоны служба не трогает вообще, поэтому изменения действуют сразу. Новый список шаблонов используется для подсчёта со следующего прохода. |
| Убрал шаблон человеку, которого служба сейчас держит в блокировке | Блокировка снимается в срок как обычно, дальше доступ определяется новыми шаблонами. |
| **Разблокировал** человека вручную, пока у него стоит блокировка службы («пусть поест ещё раз») | Это решение оператора: блокировка службы закрывается как «снята оператором», и **до конца этого окна служба этого человека повторно не блокирует**. |
| **Заблокировал** человека сам (по своей причине), в том числе поверх блокировки службы | Служба помечает блокировку как «перехвачена оператором» и **никогда её не снимает**. На панели «Активные блокировки» появляется отметка «заблокирован оператором». |
| Человек был заблокирован оператором до прохода | Служба его не трогает и не запоминает (проверка `is_block` перед блокировкой). |
| Уволил сотрудника или сделал неактивным | Служба не разблокирует уволенного и закрывает запись. |
| Изменил время окна (например, ужин до 20:00) | Время снятия блокировки пересчитывается по новому окну при каждом обновлении расписаний (раз в 10 мин и при событии «Редактирование временной зоны»), но не больше предельного срока `max_hours`. Окно продлили — блокировка держится дольше, сократили — снимается раньше. |
| Создал запись планировщика «Блокировка» на дату | Это тоже блокировка оператором: служба её не снимает. |
| Отредактировал сотрудника, но блокировку не трогал | Ничего не происходит. При снятии блокировки служба меняет только `is_block` (частичный `POST /users/staff?ids=`), поэтому остальные правки оператора не затираются. |

Перед снятием блокировки служба всегда проверяет, что человек действительно заблокирован, и смотрит в журнале,
не было ли после её блокировки действий оператора с этим сотрудником. Если ситуация непонятна, служба **не снимает**
блокировку и выводит предупреждение. Решает человек.

## Переключатель «Блокировка повторов» (кнопка безопасности)
В шапке всех экранов есть индикатор режима:
- **ВЫКЛ** (серый) — режим по умолчанию: работает как сейчас, только дашборд, PERCo не меняется. Это «старый метод».
- **ТЕСТ** (жёлтый) — блокируются только сотрудники из списка `test_user_ids`.
- **ВКЛ** (зелёный) — блокируются все.

Нажатие на индикатор открывает окно: ввести PIN администратора и выбрать режим. При переходе в «ВЫКЛ» служба
**сразу снимает все свои текущие блокировки** и показывает, со скольких человек сняла, а у кого не получилось.
Режим сохраняется в базе и переживает перезапуск. Флаг `blocking.force_off: true` в config.yaml отключает
блокировку жёстко, независимо от кнопки.

Ещё на экране «Рабочее место» есть панель **«Активные блокировки»**: кто, за какой приём пищи, до какого времени,
и кнопка «Разблокировать» у каждой строки (тоже по PIN).

- `internal/engine/blocker.go` (новый): решение «блокировать или нет» после первого прохода в окне, цикл снятия

- `internal/web`: `GET /api/blocking` (режим и активные блокировки), `POST /api/blocking/mode`,
  `POST /api/blocking/release/{id}`, `POST /api/blocking/release-all` — все POST-запросы с PIN.
  На экранах: индикатор режима, панель блокировок, окно с PIN.
- `cmd/perco-meal`: команда `unblock-all`.
- `config.yaml`: секция `blocking: {force_off, admin_pin, test_user_ids, max_hours: 16, planner_safety: true}`.

## Результаты этапа 0 (12.10.2026, Бабаева id 958 и Раббимова id 960)
- `POST /users/staff?ids=<id>` с телом `{"is_block": true|false}` → `{"result":"ok"}`. В карточке меняется **только**
  `is_block`. После разблокировки карточка байт в байт совпадает со снимком «до».
- PERCo реализует блокировку через **планировщик**: появляется запись типа 5 на сегодня («Заблокирована карта» / value 1,
  `end_date: null`). При разблокировке запись того же дня **заменяется** на «Разблокирована карта» / value 0,
  поэтому записи не копятся.
- События в журнале: 501404 «Блокировка сотрудника», 501405 «Снятие блокировки сотрудника», 501409 «Добавление записи
  планировщика», у всех есть `user_name` оператора.
- Отказ при заблокированной карте: **код 8 «Запрет прохода»**, считыватель пищит. Карту, приложенную через 18 с после
  блокировки, контроллер уже отклонил (точная задержка меньше).
- После разблокировки карта снова проходит (код 17, зелёный).
- Ещё не проверено: страховка через планировщик (снимет ли PERCo блокировку сам, если поставить `end_date` = сегодня).
  Для этого нужна проверка через ночь на тестовом сотруднике.

4. Планировщик: запись типа 5 на завтра создаётся и удаляется. Если её не удалять, разблокирует ли PERCo в полночь сам.

## Известные ограничения
- Между первым проходом и срабатыванием блокировки проходит несколько секунд. Если в этот момент приложить карту
  повторно, получится зелёный. Такой проход будет помечен красным «повтор» в дашборде и отчёте.
- Модуль WM04 (API) работает в ознакомительном режиме до ~07.12.2026. Без ключа служба перестанет видеть проходы и
  блокировать. Fail-open: заблокированные к этому моменту будут разблокированы ночной страховкой PERCo
  (если этап 0 её подтвердит). Команда `unblock-all` тоже работает через API и в этом случае не поможет:
  тогда снимать блокировку нужно в интерфейсе PERCo (Сотрудники → фильтр «Заблокированные» → разблокировать).
