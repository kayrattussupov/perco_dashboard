# План: чтение из базы PERCo, запись через API, упор на отказоустойчивость

> Статус: план, код не начат. Дополняет [plan-blocking.md](plan-blocking.md): правила блокировки там,
> здесь — откуда служба берёт данные и как переживает сбои.

## 1. Цели (проверяемые)

| № | Цель | Как проверяем |
|---|---|---|
| Ц1 | Никто не остаётся заблокированным дольше своего срока, **даже если служба или ПК выключены** | блокировка с `end_date` снимается PERCo без службы (этап 4) |
| Ц2 | Ни одной записи в PERCo, пока контроллер не на связи или связь мигает | тест «связь мигает», журнал |
| Ц3 | Нагрузка на PERCo-Web ограничена сверху, независимо от числа людей и сбоев | бюджет запросов (раздел 6), счётчики на дашборде |
| Ц4 | Сбой PERCo, базы, сети или лицензии не требует ручных действий: служба переходит в безопасный режим и сама возвращается | тесты отказов (раздел 9) |
| Ц5 | Дашборд показывает проходы и повторы, даже когда блокировки невозможны | режимы деградации (раздел 5) |
| Ц6 | Любое неожиданное состояние видно на дашборде за минуту, а не по жалобам | панель «Состояние службы» (раздел 8) |

## 2. Принципы

1. **При сомнении не блокируем (fail-open).** Лишний обед дешевле голодного человека. Действует везде ниже.
2. **В базу PERCo не пишем никогда.** Контроллер получает изменения только от сервера PERCo-Web; строка,
   изменённая в базе напрямую, до контроллера не дойдёт и разведёт базы. Пользователь базы — только `SELECT`.
3. **Снятие блокировки — забота PERCo, служба — страховка.** Блокировка ставится сразу со сроком (`end_date`),
   PERCo снимает её сам. Служба всё равно снимает в срок, если PERCo не снял. Два независимых пути.
4. **Ограниченная работа.** У каждого запроса таймаут, у каждой очереди предел, у каждого цикла пауза.
   Никакая ошибка не превращается в шквал запросов.
5. **Один писатель.** В PERCo пишет ровно один экземпляр службы.
6. **Гистерезис.** Связь «восстановилась» только после 2 минут без сбоев; источник данных переключается
   после нескольких ошибок подряд, а не после одной. Мигание не вызывает метаний.
7. **Всё видно.** Каждое отклонение — на дашборде и один раз в журнале, без спама.

## 3. Что из базы, что через API

**Из базы (только чтение, `127.0.0.1:3306`, база `perco`):** всё, что PERCo уже записал.

| Данные | Запрос | Как часто |
|---|---|---|
| Новые события | `id > курсор − 200 ORDER BY id LIMIT 500` (хвост — от пропусков, см. 4.2) | раз в 1 с |
| Кто заблокирован | `is_block = 1` среди активных | раз в 10 с |
| Блокировка конкретного человека до/после записи | по `id` | при записи |
| Сотрудники, подразделения, шаблоны | весь справочник; сравнение с прошлым по хэшу | раз в 5 мин |
| Окна питания (шаблоны → расписания → интервалы) | 1 запрос | раз в 5 мин |
| Записи планировщика (блокировки с `end_date`) | по сотрудникам службы | раз в 1 мин |
| ФИО | из базы, **если не зашифрованы**; иначе API `fullList` | раз в час |

**Через API:** то, что должно дойти до контроллера, и то, чего нет в базе.

| Действие | Запрос | Ограничение |
|---|---|---|
| Блокировка (со сроком) | `POST /users/staff?ids=…` | пачка раз в 5 с, только при устойчивой связи |
| Снятие (страховка) | то же, `is_block: false` | пачками по 50, следующая — когда очередь контроллера пуста |
| Сброс зональности | `/devices/{id}/command` | как сейчас |
| Связь с контроллером, очередь команд | `/devices/state`, `/devices/{id}/errors` | раз в 30 с; перед записью, если показание старше 5 с |
| Фото | `/users/staff/{id}` | только новые и изменившиеся сотрудники |

**Запасной режим:** если база недоступна, всё «из базы» читается через API в нынешнем облегчённом
режиме (события раз в 2 с, заблокированные раз в минуту, сотрудники раз в час).

## 4. Чтение из базы: как не потерять события

1. **Курсор по `id` + перечитывание хвоста.** В MySQL строка с меньшим `id` может закоммититься позже большей.
   Каждый опрос берёт `id > курсор − 200`; повторы отсекает `InsertEvent` (уникальный `id`).
2. **Поздние события.** Если события, переданные контроллером после восстановления связи, получают
   новые `id` — курсора хватает. Если `id` по времени события — раз в 5 мин перечитываем последние 2 часа по времени.
   Решается разведкой (раздел 10).
3. **Сверка за день.** Раз в час: число событий нашего устройства за сегодня в базе и в SQLite.
   Разница → полное перечитывание дня и предупреждение на дашборде.
4. **Проверка структуры при запуске и раз в час.** Нужные таблицы и колонки на месте, типы те же.
   Не совпало (например, после обновления PERCo) → запасной режим API, красная плашка «структура базы изменилась».
5. **Защита самой базы.** Пользователь `meal_ro`: только `SELECT`, `MAX_USER_CONNECTIONS 2`.
   У запросов таймаут 5 с (`MAX_EXECUTION_TIME`), всегда `LIMIT`, одно соединение. Индексы проверяем
   до запуска: запрос не должен читать всю таблицу событий.

## 5. Режимы деградации

| База | API | Контроллер | Что работает |
|---|---|---|---|
| ✅ | ✅ | ✅ | всё |
| ❌ | ✅ | ✅ | всё, чтение через API (облегчённый режим), жёлтая плашка |
| ✅ | ❌ | любое | дашборд и повторы (красным); **новые блокировки не ставятся**; уже поставленные снимет PERCo по `end_date` |
| ✅ | ✅ | ❌ или мигает | дашборд; **записи откладываются**, пока связь не устойчива 2 мин и очередь PERCo не пуста |
| ❌ | ❌ | любое | дашборд показывает последние данные с плашкой «нет данных с ЧЧ:ММ»; записей нет |
| ПК выключен | | | блокировки снимает PERCo по `end_date`; после включения служба догоняет события и сверяет блокировки |

Переход в любой режим и выход из него — одна строка в журнале и плашка на дашборде.

## 6. Бюджет нагрузки на PERCo

Жёсткие пределы в коде (не настройки):

| Канал | Предел |
|---|---|
| API, всего | ≤ 1 запрос/с в среднем за минуту, не больше 1 одновременно |
| API, записи | 1 запрос в 5 с (пачка), снятие — пачки по 50 с ожиданием пустой очереди |
| API, таймаут | чтение 10 с, запись 10 с |
| API при сбоях | автомат-выключатель: после 3 ошибок подряд пауза 30 с, затем один пробный запрос |
| База | ≤ 2 запроса/с, 1 соединение, таймаут 5 с |

**Пик 200–400 человек в час** (считыватель один, физически не больше 12–20 проходов в минуту):

| | Сейчас | По плану |
|---|---|---|
| Блокировки | 3 запроса на человека → до 1200/ч | пачки раз в 5 с → до 720/ч в пик, обычно меньше |
| Снятия | 3 на человека → до 1200/ч | 0, снимает PERCo; страховка — пачки по 50 |
| Фоновое чтение API | ≈ 1 запрос в 2 с + таблица сотрудников раз в минуту | 2 запроса в 30 с |

**Задержка доставки в контроллер** — главный неизвестный предел: одну блокировку контроллер получил
быстрее 18 с, как он справится с 400 в час — неизвестно. Служба следит за очередью (`cmd_count`):
если она больше 50 или не убывает 5 минут, новые блокировки приостанавливаются, на дашборде предупреждение.
Повтор прохода в первые ~20 с всё равно пройдёт: это предел контроллера, его закрывает экран «уже ел».

## 7. Карта отказов

| Сбой | Как заметим | Что делает служба | Что видит человек |
|---|---|---|---|
| PERCo-Web завис или медленный | таймауты API | автомат-выключатель, пауза 30 с; записи ждут; блокировки снимет PERCo | жёлтая плашка |
| База недоступна | ошибка соединения 3 раза подряд | запасной режим API; проба базы раз в минуту | жёлтая плашка |
| Структура базы изменилась (обновление PERCo) | проверка структуры | запасной режим API | красная плашка с названием таблицы |
| Контроллер не на связи | `/devices/state` | записи откладываются | красный статус в шапке |
| Связь мигает (14–15.10) | несколько смен состояния за 10 мин | записи только после 2 мин устойчивой связи и пустой очереди | «связь неустойчива» |
| У ПК пропала сеть (15.10) | ошибки «unreachable network» | как «PERCo-Web завис»; при `url: 127.0.0.1` служба продолжает видеть PERCo | жёлтая плашка |
| Очередь контроллера растёт | `cmd_count` > 50 или не убывает 5 мин | новые блокировки на паузе | предупреждение |
| Истекла лицензия WM04 | ответ API 402/403 или текст про лицензию | блокировки выключены, чтение из базы продолжается | красная плашка; предупреждение за 30 дней до `license_until` из конфига |
| Служба упала посреди записи | строка «pending» в журнале при старте | доводит или откатывает (уже есть) | — |
| ПК выключен или спит | разрыв во времени при старте | догоняет события; снимает просроченные; PERCo уже снял по `end_date` | — |
| Два экземпляра службы | в журнале PERCo есть блокировки нашим логином, которых нет в нашем журнале | **запись в PERCo запрещается**, красная плашка | «работает второй экземпляр» |
| Часы ПК разошлись с PERCo | разница времени событий > 2 мин (уже есть) | блокировки не ставятся | предупреждение |
| Окна питания не загрузились | пустой список | блокировки не ставятся (уже есть) | плашка |
| Оператор правит блокировки вручную | события 501404/501405 не от службы (уже есть) | последнее слово за человеком | — |
| SQLite повреждён или диск полон | ошибка записи; свободно < 1 ГБ | блокировки не ставятся; дашборд из памяти | красная плашка |
| Служба блокирует не того | контроль на дашборде, плановые проверки | `force_off`, кнопка «ВЫКЛ», `unblock-all` (уже есть) | — |

## 8. Наблюдаемость

Панель «Состояние службы» на дашборде (видна всем, обновляется раз в 10 с):
- источник данных (база / API), возраст последних данных;
- запросов к API за последнюю минуту и час, ошибки, состояние автомат-выключателя;
- очередь контроллера и время доставки последней блокировки;
- блокировок поставлено / снято PERCo по сроку / снято службой (страховка) — если страховка срабатывает часто, `end_date` не работает;
- дата лицензии WM04, свободное место на диске, время последней резервной копии SQLite.

Журнал: одна строка на смену состояния, ошибки повторяются не чаще раза в минуту, файл ротируется
(7 дней). Резервная копия `perco-meal.db` раз в сутки, хранится 7 копий.

## 9. Проверка

**Автотесты отказов** (поддельные база и API, `go test`):
- API зависает, отвечает 500, 401 по кругу, 402 (лицензия) — нагрузка не растёт, записи не уходят;
- в базе события с пропуском и с поздним коммитом меньшего `id` — ничего не теряется;
- структура базы другая — переход на API;
- связь мигает каждые 30 с — ни одной записи;
- второй экземпляр — запись запрещена;
- прогон реального дня событий в 10× скорости — бюджет запросов (раздел 6) не превышен.

**На месте, только безопасное** (тестовая карта id 960, режим ТЕСТ):
- блокировка с `end_date` на 5 мин: PERCo снимает сам, контроллер пускает;
- общее снятие пачкой из 2–3 тестовых сотрудников;
- служба остановлена во время блокировки → PERCo снимает по сроку;
- выдернуть сетевой кабель ПК на минуту в режиме ТЕСТ → записи ждут, после возврата всё сходится.

Останавливать MySQL или PERCo-Web на рабочем сервере для теста **нельзя**: отказы базы и API проверяются
только автотестами.

## 10. Разведка базы (до кода, только чтение)

1. Таблицы событий, сотрудников, шаблонов, расписаний, планировщика; совпадают ли поля с API.
2. Порядок `id` у поздних событий (после восстановления связи).
3. Где `is_block`, совпадает ли с API сразу после блокировки.
4. Как хранится блокировка в планировщике, есть ли `end_date`.
5. Зашифрованы ли ФИО и фото.
6. Индексы по `id` и времени событий; размер таблицы событий.
7. Версия PERCo-Web и MySQL — чтобы проверка структуры знала, с чем сравнивать.

## 11. Этапы

Каждый этап — отдельный PR. Переход дальше только если выполнено условие, иначе откат.

| Этап | Что | Условие перехода | Откат |
|---|---|---|---|
| 0 | Защиты без базы: автомат-выключатель, бюджет запросов, гистерезис связи, второй экземпляр, лицензия, панель состояния, ротация журнала и резервная копия | неделя без записей при неустойчивой связи; нагрузка в бюджете | вернуть прошлую версию службы |
| 1 | Разведка базы, пользователь `meal_ro` | ответы на все пункты раздела 10 | удалить пользователя |
| 2 | Чтение из базы в режиме «сравнение»: служба читает и из базы, и из API, использует API, расхождения пишет в журнал | 7 дней без расхождений | убрать `db:` из конфига |
| 3 | База — основной источник, API — запасной | 7 дней; бюджет API выполнен | убрать `db:` из конфига |
| 4 | Тесты на месте: `end_date`, пачки, остановка службы | все проверки раздела 9 «на месте» прошли | — |
| 5 | Блокировки со сроком, пачками; служба — страховка | 2 недели: страховка почти не срабатывает, очередь контроллера в норме | вернуть снятие службой |

Этап 0 не зависит от базы и даёт основную часть стабильности, поэтому идёт первым.

## 12. Риски и открытые вопросы

- **`end_date` может не работать** (не проверено). Тогда снятие остаётся за службой, а Ц1 при выключенном ПК
  не выполняется. Смягчение: ИБП и запрет сна для ПК, блокировки не держатся на ночь (уже так).
- **Структура базы не документирована** и может поменяться при обновлении PERCo. Смягчение: проверка
  структуры, запасной режим API, режим «сравнение» после каждого обновления PERCo.
- **Пароль администратора базы** знает только установщик PERCo. Без него этапы 1–3 откладываются, этап 0 — нет.
- **Лицензия WM04** нужна для записи через API. Ключ ввести до ~07.12.2026.
- **ПК:** запретить сон, отключить экономию питания сетевого адаптера, обновления Windows — вне часов питания,
  желательно ИБП. Это вне кода, но без этого остальное слабее.
