# План: чтение из базы PERCo, запись через API

## Принцип

1. **Из базы читаем то, что PERCo уже записал**: события, сотрудники, шаблоны, окна, флаг блокировки.
   API отдаёт те же строки из той же базы, только через веб-сервер, авторизацию и JSON. Прямое чтение
   даёт тот же результат без нагрузки на PERCo-Web.
2. **Через API делаем то, что должно дойти до контроллера**: блокировку, снятие, сброс зональности.
   Контроллер получает изменения только от сервера PERCo-Web; строка, изменённая в базе напрямую,
   до контроллера не дойдёт и разведёт базы. **В базу не пишем никогда.**
3. **Через API читаем то, чего в базе нет**: живое состояние связи с контроллером и очередь команд
   (`/devices/state`, `/devices/{id}/errors`). Это память сервера PERCo, а не таблица.
4. Пользователь базы — только `SELECT` на `perco.*`, подключение к `127.0.0.1:3306`.
5. Если база недоступна или её структура не та, служба читает через API (нынешний облегчённый режим)
   и пишет об этом в журнал. Ничего не останавливается.

## Каждое обращение службы: откуда брать

| Что | Где в коде | Сейчас (API) | Будет | Почему |
|---|---|---|---|---|
| Новые события | `engine.poll` | `/eventsystem` по времени, раз в 2 с, перекрытия 30 с / 10 мин / день | **база**: `id > курсор`, раз в 1 с | один запрос по индексу, без перечитываний |
| Кто заблокирован | `BlockedLoop`, `strayBlocks` | вся таблица сотрудников раз в минуту | **база**: `is_block = 1`, раз в 10 с | маленький запрос, свежее |
| Блокировка до/после записи | `OnPass`, `release`, `reconcilePending`, удержанные | `/users/staff/{id}` ×2 на запись | **база** | API читает ту же строку |
| Сотрудники, подразделения, шаблоны | `syncStaff` | 1 + 851 запрос раз в час | **база**: 1–2 запроса раз в 5 мин | |
| ФИО | `syncStaff` | `fullList` | база, **если не зашифровано**; иначе API `fullList` (1 запрос в час) | PERCo-Web 2 шифрует часть данных |
| Фото | `syncStaff`, `fetchStaff` | в ответе `/users/staff/{id}` | API, только для новых и изменившихся | фото может лежать файлом или зашифровано |
| Окна питания | `loadMeals` | шаблон + расписания, раз в 10 мин | **база**: 1 запрос | |
| Связь с контроллером, очередь | `HealthLoop`, `linkUp`, `checkSettled`, проверки | `/devices/state` + `/errors`, раз в 15 с | **API**, раз в 30 с и перед записью | в базе этого нет |
| Блокировка | `OnPass` | `POST /users/staff?ids=` | **API** | должна дойти до контроллера |
| Снятие блокировки | `release`, `ReleaseAll` | по одному | **API, одним запросом на всех** (если подтвердится) | см. ниже |
| Сброс зональности | `backupReset` | `/devices/{id}/command` | **API** | команда контроллеру |

## Как сократить запросы к API

1. **Проверки — из базы.** Запись остаётся одна, проверки до и после читаются из базы: 1 запрос к API
   на блокировку вместо 3.
2. **Общее снятие.** `POST /users/staff?ids=1,2,3` уже принимает список. В конце окна снимаем всех
   одним запросом, потом сверяем по базе; кого не сняло — повторяем по одному.
3. **Блокировка с окончанием (`end_date`).** PERCo хранит блокировку как запись планировщика с полем
   `end_date`. Если PERCo сам снимает её в срок, снятие исчезает совсем и люди разблокируются, даже
   когда служба или ПК выключены.
4. **Записи по одной, только при связи с контроллером** — как сейчас.

Одно питание, около 130 человек:

| | Блокировка | Снятие | Всего к API |
|---|---|---|---|
| Сейчас | 3 × 130 | 3 × 130 | ≈ 800 |
| Проверки из базы + общее снятие | 130 | 1 | ≈ 131 |
| С `end_date` | 130 | 0 | ≈ 130 |

Фоновое чтение API: сейчас ≈ 3 запроса в 2 с плюс таблица сотрудников раз в минуту; будет ≈ 2 запроса
в 30 с (состояние связи).

## Что проверить на базе до кода (только чтение)

1. Список таблиц; где события, сотрудники, шаблоны, расписания, устройства.
2. Колонки событий: `id`, время, код события, сотрудник, устройство, оператор — совпадают ли с тем,
   что отдаёт `/eventsystem`.
3. **Порядок `id` у поздних событий.** Событие, которое контроллер передал после восстановления связи,
   получает новый (больший) `id` или его `id` по времени события? От этого зависит, можно ли читать
   только `id > курсор`.
4. **Пропуски при одновременной записи.** В MySQL строка с меньшим `id` может появиться позже большей.
   Поэтому курсор всегда перечитывает хвост (последние ~200 `id`), а повтор отсекает `InsertEvent`.
5. Где `is_block`; совпадает ли с API сразу после блокировки.
6. Зашифрованы ли ФИО и фото.
7. Индексы на `id` и времени событий (чтобы запрос не читал всю таблицу).

## Этапы

1. **Разведка базы** по списку выше; создать пользователя только на чтение.
2. **Код:** интерфейс источника данных, реализация «база», API — запасной вариант; проверка структуры
   при запуске; тесты на курсор, хвост и переход на API.
3. **Включить чтение из базы.** Записи не меняются, риск минимальный. Неделю сравнивать с API
   (число событий за день, список заблокированных).
4. **На месте, тестовая карта (id 960):** общее снятие нескольких людей; блокировка с `end_date`
   на 5 минут — снимет ли PERCo сам и дойдёт ли до контроллера.
5. **Переделать блокировки** под то, что подтвердилось на шаге 4.

Шаги 1–3 не трогают блокировки. Шаги 4–5 — только после проверки на тестовой карте.

## Откат

Чтение из базы включается настройкой `db:` в `config.yaml`. Без неё служба работает как сейчас, через API.
