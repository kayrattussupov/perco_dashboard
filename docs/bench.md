# Замер блокировки пачкой и нагрузки на PERCo (`perco-bench.exe`)

Утилита отвечает на два вопроса плана [plan-db.md](plan-db.md):

1. **Сколько секунд занимает блокировка пачкой из 5 человек**: ответ API → флаг записан в PERCo →
   изменение доставлено в контроллер (очередь команд PERCo опустела). То же для снятия.
2. **Какую нагрузку чтением PERCo-Web выдерживает без замедления**: ступени 1 → 2 → 4 запроса в секунду.

## Безопасность (встроено в утилиту)

- Трогает **только** сотрудников из `blocking.test_user_ids` в `config.yaml`, не больше 10.
- Без `-yes` ничего не пишет: только проверки и замер чтения.
- Перед записью проверяет: все тестовые сотрудники активны и **не заблокированы** (чужую блокировку не трогает),
  контроллер на связи, очередь команд пуста. Иначе останавливается, ничего не записав.
- Перед каждым повтором ждёт, пока контроллер примет предыдущие изменения.
- **Всегда снимает блокировку** перед выходом, в том числе после ошибки и Ctrl+C. Если не удалось
  за 5 минут, пишет `!!! НЕ УДАЛОСЬ СНЯТЬ БЛОКИРОВКУ` со списком id.
- Формат списка id (`ids=1,2` / `[1,2]` / `ids=1&ids=2`) подбирает сам и после каждой пробы сверяет список всех
  заблокированных в PERCo: если зацепило постороннего, останавливается и называет его id.
- Нагрузка чтением: не больше 5 запросов в секунду, запросы по одному (не копятся), пауза 30 с между ступенями;
  останавливается при первой ошибке или если 95% ответов дольше 3 с.

## Что подготовить

1. **Пять тестовых сотрудников в PERCo-Web** (делает администратор PERCo). Сейчас тестовый только один
   (Раббимова, id 960). Для пачки из 5 нужны ещё 4:
   - отдельное подразделение «ТЕСТ», ФИО вида «Тест Пачка 1…4»;
   - карта с **неиспользуемым** номером (иначе контроллеру нечего менять и замер «доставлено» ничего не покажет);
   - шаблон питания, как у обычных сотрудников, чтобы карта попала в контроллер;
   - узнать их id: `.\perco-bench.exe -find Тест` (только чтение, покажет id и ФИО).
2. Дописать id в `config.yaml` службы: `test_user_ids: [960, <id1>, <id2>, <id3>, <id4>]`.
3. Время: **вне окон питания**, когда контроллер на связи.
4. На дашборде переключить «Блокировка» в **ВЫКЛ** на время замера, чтобы служба не реагировала на тестовые блокировки.

## Запуск (на сервере PERCo, в папке службы `C:\PercoMeal`)

Скопируйте `perco-bench.exe` в `C:\PercoMeal` (рядом с `config.yaml`) и откройте там PowerShell.

1. Проверка без записи:
   ```
   .\perco-bench.exe -ids 960,<id1>,<id2>,<id3>,<id4>
   ```
2. Замер блокировки пачкой, 3 повтора (около 3–5 минут):
   ```
   .\perco-bench.exe -ids 960,<id1>,<id2>,<id3>,<id4> -yes
   ```
3. Проверка нагрузки чтением (около 2–3 минут):
   ```
   .\perco-bench.exe -load -yes
   ```

Каждый запуск пишет отчёт `bench-ГГГГММДД-ЧЧММСС.txt` рядом с `config.yaml`. Пришлите его.

Параметры: `-find <текст>` найти id по ФИО, `-rounds 3` повторов, `-hold 20s` сколько держать блокировку, `-timeout 2m` предел ожидания этапа,
`-idsfmt auto|comma|json|repeat`, `-steps 1,2,4` ступени нагрузки, `-step 30s` длительность ступени.

## Как читать отчёт

```
повтор 1, блокировка: ответ API 0.3 с, записано в PERCo 1.1 с, доставлено в контроллер 6.4 с (макс. очередь 5)
ИТОГ блокировка пачкой из 5 (3 замеров): ответ API мин …; записано …; доставлено в контроллер …
ступень 4 запр/с: выполнено 118, ошибок 0, мин 0.05 с, сред 0.09 с, p95 0.15 с, макс 0.30 с
```

- **доставлено в контроллер** — главная цифра: через сколько секунд после прохода повтор будет отклонён.
- **макс. очередь** — сколько команд PERCo ждало отправки; если растёт с размером пачки, контроллер — узкое место.
- **фон: лёгкий запрос и опрос событий** — если опрос событий во много раз медленнее, тяжёл сам запрос событий
  в PERCo (большая история, нет индекса), и частота тут вторична.
- **p95** на ступенях нагрузки — если растёт от ступени к ступени, PERCo-Web уже на пределе.

## Разведка API (`-discover`, только чтение)

```
.\perco-bench.exe -discover
```

Сохраняет описание API PERCo-Web в `perco-api-docs.json` рядом с `config.yaml`, выписывает в отчёт методы про блокировку,
планировщик и даты окончания, и показывает поля блокировки/дат в карточке первого из `test_user_ids` (без ФИО и фото).
Нужно, чтобы выяснить, как поставить блокировку со сроком (`end_date`), до проверки на тестовой карте.

## Что проверить вручную

Описание API на сервере: `http://192.168.1.106/api-docs` — есть ли у `/eventsystem` отбор по устройству
(параметр вроде `device`/`deviceId`). Если есть, служба будет получать события только нашего контроллера.

## Чего утилита не меряет

- Время, когда **считыватель** реально начнёт пищать: для этого после блокировки приложите карту Раббимовой
  и сравните время события 8 «Запрет прохода» с моментом блокировки в отчёте.
- Нагрузку записью на реальных людях и полноценный стресс-тест PERCo: на рабочей системе это недопустимо.
  Пиковый час (200–400 проходов) оцениваем по цифрам: время пачки × число пачек в час.
